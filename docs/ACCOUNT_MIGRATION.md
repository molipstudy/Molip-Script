# 공용 프로필 최종 단일화

최종 프로필 테이블은 **`molip_profiles.profiles` 하나**입니다. 로그인 아이디·표시 이름·사진을 보관합니다. 이메일과 인증은 `auth.users`, 관리자 권한은 `molip_profiles.admin_grants`에 둡니다.

`molip_profiles.service_registrations`는 사용자 UUID·서비스·가입 시점·가입 경로만 담는 연결 기록입니다. 프로필 복제나 유료 멤버십 테이블이 아니며 서비스별 관리자 조회 범위를 구분합니다.

## 지금 적용할 순서

1. `molip-profiles-finalize-prepare.sql`을 SQL Editor에서 실행합니다. 공용 RPC·서비스 이용 기록·알림 경로와 단어장 FK를 준비합니다. 아직 기존 프로필 테이블은 삭제하지 않습니다.
2. 몰입 스크립트와 **Molip_Voca_Server**의 수정된 코드를 배포합니다. 단어장 프런트엔드의 가입 서비스 표기도 함께 배포할 수 있습니다. 이 상태에서 프로필 조회/수정과 스크립트 로그인, 커뮤니티, 단어장 협업자를 확인합니다.
3. 배포 후 기존 스크립트 탭·PWA도 새로고침해 새 코드를 사용하는 것을 확인한 뒤 `molip-profiles-finalize.sql`을 실행합니다. 이때 `public.profiles`, `public.molip_script_profiles`, `molip_script.profiles`와 동기화 트리거·함수가 제거됩니다. 뷰로 다시 만들지 않습니다.
4. 읽기 전용으로 테이블 제거·UUID·FK·학습 데이터·관리자 권한·새 가입 알림을 검증합니다.

두 SQL은 각각 한 트랜잭션입니다. 실패한 트랜잭션은 롤백되지만, 성공 후 되돌리려면 별도 복구가 필요하므로 적용 전 백업을 확보합니다. 각각 한 번만 실행하며 1차 `molip-profiles-upgrade.sql`은 다시 실행하지 않습니다. **현재 2차 SQL은 운영 DB에 적용하지 않았습니다.**

## 함께 수정한 프로젝트

- Molip-Script: 로그인·가입·계정 조회는 기존 RPC 이름을 유지하고 공용 원본을 사용합니다.
- Molip_Voca_Server: public 프로필 직접 조회/upsert와 외래키 자동 join을 제거하고 공용 프로필 RPC로 전환합니다. 공개 작성자 정보에는 이메일을 반환하지 않습니다. 협업자 이메일 조회·초대는 소유자/본인 권한을 확인합니다.
- Molip_Voca_Frontend: 가입 서비스 출처만 명시하며 API 응답 형식은 유지합니다.

## Exposed schemas / tables

현재 앱이 사용하는 `public`, `molip_script`, `molip_voca`의 RPC·서비스 테이블만 필요한 권한으로 사용합니다. `molip_profiles`와 `molip_notifications`는 클라이언트가 직접 조회하지 않으므로 API 노출에 추가할 필요가 없습니다. `admin_grants`, `profiles`, `service_registrations`, 알림 events에 표준 Data API 권한을 부여하지 않습니다.

Supabase의 custom grants 경고는 개별 권한이 기본값과 다르다는 뜻입니다. 경고 제거를 위해 전체 권한으로 덮어쓰지 않습니다. 단어장·커뮤니티는 기존 RLS와 필요한 권한을 유지하고 공통 계정/관리자 내부 테이블은 접근을 차단합니다.

## 검증

메모리 PostgreSQL 테스트로 프로필 3개 제거, 단어장 외래키 5개 전환, 기존 스크립트 보존, 공개 이메일 비노출, 자기 계정 수정, 협업자 권한, 신규 가입 시 공용 프로필 단일 생성·서비스 기록 중복 방지·가입 알림 1회 전송을 검증합니다. 이는 운영 배포 후 최종 확인을 대체하지 않습니다.

## 1차 이전 이력

# 공용 계정 이전 — molip_profiles

2026-11-14 운영 DB의 테이블·외래키·정책·함수·트리거를 읽기 전용으로 확인해 작성했습니다. **1차 이전은 운영 DB에 적용됐고 읽기 전용으로 검증했습니다. 아래 호환 계층 설명은 1차 상태입니다.** 전체 이전 SQL은 `molip-profiles-upgrade.sql`입니다.

## 확인 결과

직접 집계에서 auth 계정·public 프로필·script 프로필은 각각 12개였고, public/script UUID는 12개 모두 일치했습니다. 빈 `public.molip_script_profiles`와 관리자 등록 0개도 확인했습니다. 이는 조회 시점의 결과이며 SQL 실행 때 다시 충돌 검사를 합니다.

`public.profiles.username`은 표시 이름, `molip_script.profiles.login_id`는 로그인 아이디입니다. 같은 값이라고 추정하지 않습니다. 단어장 5개 테이블이 `public.profiles`를 FK로 참조하며, 단어장 서버가 이 테이블에 직접 upsert합니다. 따라서 테이블을 옮기고 같은 이름의 뷰를 만드는 방식은 이번 이전에 사용하지 않습니다.

## 최종 원본과 호환 계층

| 위치 | 상태 |
| --- | --- |
| `auth.users` | 인증·이메일 원본 유지. 데이터·컬럼·트리거 DDL 변경 없음 |
| `molip_profiles.profiles` | 공용 프로필 원본. UUID, nullable 전역 login_id, 기존 username/profile_image, 시점 |
| `molip_profiles.admin_grants` | 관리자 권한 원본. user_id+scope 고유, granted_at, granted_by |
| `public.profiles` | 기존 단어장 API·FK를 위한 물리 호환 테이블 유지 |
| `molip_script.profiles` | 배포된 스크립트 앱·커뮤니티·가입 알림을 위한 물리 호환 테이블 유지 |
| `public.molip_script_profiles` | 사용처 최종 확인 전 보존. 기존 쓰기도 공용 원본에 반영 |
| `molip_admin` | 권한 복사·RPC 교체·검증 후 RESTRICT로 제거. CASCADE 사용 안 함 |

이메일은 공용 프로필에 복제하지 않습니다. 로그인 해석과 관리자 화면은 `auth.users.email`을 읽습니다. 기존 테이블의 이메일은 호환 값으로 남으며, 프로필 동기화 때 Auth 값으로 갱신됩니다. Auth 이메일 변경을 가로채는 새로운 auth 트리거는 만들지 않습니다.

공용 프로필 쓰기는 기존 프로필 동기화 트리거와 권한 검사 RPC가 담당합니다. 공용 스키마는 Data API에 추가로 노출할 필요가 없고 클라이언트에 테이블 권한을 부여하지 않습니다. 기존 public 프로필의 공개 범위·서비스 RLS는 이번 SQL에서 임의로 바꾸지 않습니다. 따라서 기존 공개 프로필의 이메일 공개 범위를 줄이는 작업은 단어장 API 전환과 함께 별도 진행해야 합니다.

표시 이름·프로필 사진은 기존 단어장 프로필 수정이 공용 원본에 반영되고 반대 방향도 동기화됩니다. 기존 로그인 아이디는 보존되며, 기존 서비스 API로 조용히 바꾸지 못하도록 막습니다. 로그인 아이디가 없는 공통 계정만 인증된 자기 계정의 `register_profile` RPC로 아이디를 선택할 수 있습니다. 사용자 입력 이메일·UUID·역할을 이 RPC는 받지 않습니다.

신규 가입은 기존 `auth.users` 트리거가 호출하는 **public 소유 함수 `handle_new_user()` 본문만** 공용 프로필 생성으로 교체합니다. 관리형 auth 테이블·기존 트리거 자체는 변경하지 않습니다. 스크립트에서 입력한 login_id만 형식 검증 후 예약하고, 단어장의 username을 login_id로 추정하지 않습니다. 기존 가입 알림은 script 프로필 첫 INSERT에 계속 연결되어 과거 회원을 재발송하지 않습니다.

## 적용 순서

1. Supabase 백업/복구 지점을 확보하고 현재 스키마를 보관합니다.
2. **`molip-profiles-upgrade.sql`을 postgres로 한 번 실행**합니다. 기존 `supabase.sql`은 실행하지 않습니다.
3. 신규 스키마가 이미 있다면 SQL은 시작 중 실패합니다. 재실행·부분 적용을 추정해서 진행하지 않습니다. 한 트랜잭션으로 실행하므로 중간 오류가 나면 변경 전체가 롤백됩니다.
4. `molip_profiles.admin_grants`에 관리자를 UUID로 명시적으로 등록합니다. 누구도 자동으로 관리자로 승격하지 않습니다. 구문은 `docs/ADMIN.md` 참고.
5. DB 이전 후 이 앱 코드를 배포합니다. 새 앱은 `register_profile`·`account_profile` RPC를 사용합니다. 기존 단어장 코드는 물리 호환 테이블로 계속 작동합니다.
6. 기존 사용자 로그인·새 가입·메일 인증 후 로그인·단어장 프로필 수정·커뮤니티 공유·학습 기록·관리자 권한 부여/해제를 확인합니다.

현재 MCP는 읽기 전용이며 마이그레이션 도구를 제공하지 않습니다. 쓰기 권한을 우회하거나 execute_sql로 DDL을 보내지 않았습니다. SQL은 사용자가 실행하거나, 승인된 마이그레이션 연결에서 적용해야 합니다.

## 정합성과 검증

로그인 아이디 충돌, 한 UUID의 서로 다른 아이디, 관리자 scope 충돌이 있으면 이전을 멈춥니다. 기존 profile/권한 테이블 쓰기를 잠근 동안 복사·트리거·함수를 설정합니다. 기본 10초 잠금 대기 초과 시 실패하며, 서비스 이용 중에는 짧은 쓰기 대기가 발생할 수 있습니다.

계정 UUID 수·스크립트 아이디 매핑·기존 관리자 권한 복사를 검증한 뒤 옛 관리자 스키마를 삭제합니다. 예상하지 못한 의존성이 있으면 RESTRICT 삭제가 실패해 전체 트랜잭션이 롤백됩니다.

테스트는 운영 데이터가 아닌 합성 데이터와 메모리 PostgreSQL(PGlite)에서 실행합니다. 기존 데이터와 단어장 FK 유지, 양방향 프로필 동기화, 신규 Auth 가입, 중복 등록, 아이디 충돌, 전역/서비스 권한 범위, 일반 회원/비회원 접근 거부, 권한 즉시 해제, 충돌 시 롤백을 검증합니다. 운영 SQL 적용 후의 최종 검증을 대체하지 않습니다.

## 이후 정리

단어장·스크립트의 프로필 쓰기와 읽기를 모두 공통 RPC로 전환한 후 기존 프로필 FK와 참조를 다시 조사합니다. 그때 호환 테이블·트리거와 기존 공개 이메일 범위를 정리합니다. 지금은 데이터나 배포된 단어장 동작을 깨면서 세 테이블을 삭제하지 않습니다. 멤버십·구독 테이블은 실제 기능이 생길 때 동일한 공용 UUID를 참조하도록 추가합니다.
